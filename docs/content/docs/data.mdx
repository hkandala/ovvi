## Where things live

One rule decides where each new thing goes (D57):
- **Anything that takes space in the layout** is a multiplexer pane.
- **Transient UI** (the palette, popovers, hover, chips) lives in app memory
  only.
- **Per-device settings** live in app storage.

The installed app is `Ovvi.app`, `dev.ovvi.app`, which only `make install`
and `make dmg` build; any other Release build (`make app`, a measure) is
`dev.ovvi.app.release`, with defaults and saved windows of its own, claiming
`ovvi-release://`. A Debug build (`make run`,
the UI tests, CI) is `Ovvi Dev.app`, `dev.ovvi.app.debug`, so it has its own
defaults, saved windows, notifications, login item and browser data, and it
claims the `ovvi-dev://` scheme, not `ovvi://`. Its folders on This Mac are
`~/.config/ovvi-dev` and `~/Library/Logs/Ovvi Dev/plugins`. It never reads or
writes the installed app's. What it shares are the files that belong to the
sessions and panes both apps show: `~/.cache/ovvi` and `~/.local/state/ovvi`
on each machine, and on This Mac the herdr server jobs with their logs
(`~/Library/Logs/Ovvi/<session>.log`) and `~/Library/Caches/ovvi`, whose SSH
sockets are per app.

`scripts/reset-app-data.sh [--dry-run] [bundle id]` deletes one build's data on
This Mac for a fresh start (the installed app's by default), while that build
is not running. Run it without `sudo`. macOS keeps an app's saved windows in
`~/Library/Daemon Containers`, which needs Full Disk Access for the terminal;
the first launch after a reset closes them anyway
([Welcome](/docs/ui/welcome)). When macOS refuses to delete a folder (some
WebKit caches), the script goes on, lists what it kept and exits with 1. For a
Debug build it also deletes `~/.config/ovvi-dev` and `~/Library/Logs/Ovvi Dev`. For the installed app, and only while no Ovvi build
runs, it also deletes `~/.config/ovvi`, `~/Library/Logs/Ovvi`,
`~/Library/Caches/ovvi`, `~/.cache/ovvi` and `~/.local/state/ovvi`, which other
builds share. It never touches herdr's sessions or the agents' files.

<Callout title="Nothing the app saves describes herdr's state">
The only exception is each window's restore state: the names of its pages.
A page whose session was deleted is skipped. A fresh install on a new Mac rebuilds
every space, tab and pane from herdr.
</Callout>

## Which pages a window opens

- A restored window opens the pages in `pages` again, in order, and shows
  `page`, each with its `selection`. A session that is not running starts,
  as its Start does (a restart of the Mac stops every session; a remote
  machine connects first); a name the machine no longer lists is skipped.
  macOS hands a restored window its scene storage a moment after the window
  first shows, so the window waits for it (at most 1 s) before it opens a
  page.
- With `-session` on the command line, every window restores only that session
  (a run against a throwaway session never reopens another), with its saved
  selection, and a new window (⌘N) lists only `ovvi-*` sessions.
- With none left, the first page is the session named by the `-session`
  launch argument (a test's), else none: the window shows the
  [new-window view](/docs/ui/window#new-window). On This Mac the app starts
  `-session`'s session when it is stopped (a launchd job, D47). It never opens
  a session by itself: only a restored window starts the sessions it had.
- A new window opened for a machine (the machine menu, a machine just added) is on
  that machine and opens its `default`. File ▸ New Window (⌘N) opens no page.
- No setting names a session to open. `-session` is read from the argument
  domain only.
